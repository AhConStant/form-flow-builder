## 对照表（红字为准）

|---|---|---|---|---|
| 带勾清单 | 审批 | 审批 | **审批** | `approve` |
| 电脑+红箭头 | 通知执行 / 自动传阅分发 | 通知执行 | **通知执行** | `notice` |
| 电脑+绿箭头 | 通知申请人或执行动作 | 通知执行 | **执行动作**（用户 2026-11-25 后续明确） | `action` |

| 窗口+▼（下拉尖角） | 条件判断 / 判断人员类别 / 判断是否… | 判断 | **条件判断** | `judge` |

## 关键规则（容易搞错的地方）

1. **多选择审批 → 通知执行**（不是审批！红字明确改成了通知执行）。
2. **存档 / 归档 → 执行动作**（不是存档/通知执行，红字是执行动作）；
   但**前提是图标真的画着文件夹**：步骤名里带「归档/存档」不代表就是执行动作。
   修缮流程「12 归档处理」的图标是**窗口+红人+红斜箭头（红方块）→ 通知执行 `notice`**，
   用户 2026-11-26 11:36 指出这里识别错了、该生成独立步骤。**永远按图标判，不看步骤名猜**。
3. **自动传阅分发 → 通知执行**（图标同"通知执行"）。
4. **电脑+绿箭头（通知申请人或执行动作）→ 执行动作**（用户 2026-11-25 后续明确修正，覆盖红字表的"通知执行"；实际截图中如"2 审批开始""5.1 医技药人员""5.2 护理人员"都是这类图标 → 执行动作）。
5. 带勾清单（审批）→ 审批。
6. **「窗口+人+红斜箭头」不是判断**（用户 2026-11-26 10:46 指着「3 请选择是否需要职能科会签」「3.1.1.1 请选择是否需要主管院长审批」两张红框纠正）：
   这类「请选择是否需要…」的步骤是 **通知执行**，`type` 写 `notice`。
   **判断节点的图标是「窗口+▼（下拉尖角）」**（如「判断人员类别」「判断是否新入岗员工」），两者别混。
   判定口诀：**看标记颜色不看形状**——红标记（红箭头/红人+红斜箭头/红方块）→ 通知执行；
   绿箭头 → 执行动作（折叠）；窗口+▼ → 判断；红圈 → 结束。

## 与 flow_types.py 的关系

`flow_types.classify()` 按名称关键词判类型，但有几处与红字判定不一致，已在代码里按红字修正：

- `多选择审批` / `多选审批` / `多人选择` → `notice`（原来判 multi/审批，红字要求通知执行）
- `存档` / `归档` / `入档` / `备案存` → `action`（原来判 archive 后回退 notice，红字要求执行动作）

生成流程时，若截图中步骤带图标，按本表判定后**显式写 `graph.nodes[].type`**，不依赖自动分类。

## 执行动作节点不生成步骤，折叠成连线文字（用户 2026-11-26 明确）

- 判定为 `action`（执行动作）的节点，在流程图上**只把步骤名画在连线上、不画节点框**；
  **导出包里也不要生成这类步骤**——它们不是平台的「执行动作」步骤，而是连线上的文字。
- 实现：`build_export.py` 的 `fold_action_nodes()` 在生成 FlowStep 之前把 action 节点删掉，
  前驱直接连到后继（多出线则各自展开），原步骤名写进该条连线的 `note` / `ConContentDesc`；
  `draw` 号重新连续编号。导出的 `FlowStep` 里不应再出现 `ActionTypeID=4`。
- 若 action 的后继还是 action（如「下一步」→「判断错误」），文字用 ` → ` 连成一句
  （例：`下一步 → 判断错误`）。
- 流程图（`build_flowchart.py`）仍按 34 个节点画：action 不画框、文字压在连线上，与导出包的 23 步不对应，
  这是**有意差异**——图上要看得见「这一步是执行动作」，包里不能有这个步骤。

## 分支归属按层级序号判断（用户 2026-11-26 纠正）

- 流程步骤名的前缀序号就是层级：`5.6 判断错误` 是 `5 判断人员类别` 的子项，
  边必须写成 `5 判断人员类别 → 5.6 判断错误 → 9 结束`；
  **不要**把它挂到相邻的 `5.5.1.1.1.1.1 下一步` 后面（用户原话："这个步骤没有这条分支"）。
- 遇到「判断错误 / 退回 / 终止 / 结束」这类出口，先看序号前缀找父节点，再定边。
- 这类远离主线的出口在流程图上会走画布外侧沟槽：文字用执行动作样式（橙色 13px + 白描边）
  压在沟槽竖线中段，由 `graph.edgeLabels` 提供（键写 `父节点→目标节点`，值写步骤名）；
  导出包里该条连线 `note` 就是这段文字，不会生成额外步骤。

## 09 截图（步骤表：步骤名称 / 步骤说明 / 执行人 / 下一步）识别流程（用户 2026-11-26 定）
- 用户以后贴这种「步骤名称表」截图 = 该流程的权威结构，按下面顺序读：
  1. 序号前缀定层级与分支归属（`3.1` 是 `3` 的分支、`3.1.1.1.2` 是 `3.1.1.1` 的分支）；
  2. 图标定类型（见上表）：绿箭头/文件夹 → `action`（折叠成连线文字）、红箭头或红人+红斜箭头 → `notice`、
     带勾清单 → `approve`、窗口+▼ → `judge`、绿笔记本+加号 → `start`、红圈 → `end`；
  3. **「下一步骤」列属于同一行左侧的步骤名**（不是上一行、也不是下一行的）：
     有值就**照抄**（可以跳号，如 `9 → 11`，中间那一行不拆成串行）；为空则该行**默认接下一级**
     （序号 +1 的那一行），不要自己编目标。
  4. 跳号时被跨过去的那一行：**先看它有没有入边**。前一行「下一步」已经跳到后面、
     没人指向它 → 说明这一步**没被启用，整条流程里不要生成**（用户 2026-11-26 修缮流程原话：
     「第 10 个步骤完全没有用到就不要生成了」）。**不要**臆造成并行分支，也不要硬串成 `9 → 10 → 11`。
  5. 只有用户明确说「这两步是并行的」时，才做两条线：前一节点 `processTo`/`importantShunt`
     写两个 DrawID，两分支的 `processPrev` 都指向前驱，各自再连到同一个汇聚节点。
  6. 没有前驱、只被别的「结束」串联的重复结束节点（如 8 结束→9 结束→10 结束）合并为一个结束。
